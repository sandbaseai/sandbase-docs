# エラーとリトライ {#errors-and-retries}

エラーは、HTTP ステータス、エンドポイントの種類、操作のセマンティクスに基づいて処理してください。SandBase は複数の互換プロトコルを提供しているため、
すべてのエンドポイントに共通する単一のエラー JSON 形式はありません。

## エンドポイントのエラー形式を確認する {#read-the-endpoint-s-error-shape}

- OpenAI 互換の操作は、通常、メッセージと type を含む `error` オブジェクトを返します。
- Anthropic Messages は Anthropic 互換のエラーエンベロープを返します。
- コアプラットフォームの操作は、フラットな `{ "error": "..." }` ボディ、または文書化されたリソース固有のエラーを返す場合があります。
- Google やプロバイダーネイティブの操作は、文書化されている場合、それぞれの互換プロトコルの形式を維持します。

レスポンスの HTTP ステータスと文書化されたボディを使用してください。選択したエンドポイントが保証していない限り、`code`、`param`、
`request_id` などの任意フィールドを必須として扱わないでください。例は [API エラーリファレンス](/api-reference/errors) を、
操作ごとのレスポンスは [OpenAPI 仕様](/openapi.yaml) を参照してください。

## ステータスに応じて対応を決める {#decide-what-to-do-by-status}

| ステータス | 主な原因 | 推奨される対応 |
|---|---|---|
| `400` / `422` | 無効なボディやパラメーター、またはモデルが対応していない機能 | リトライする前にリクエストを修正します。 |
| `401` | 認証情報がない、無効、期限切れ、または失効している | 認証情報を差し替えます。 |
| `402` | 請求の状態によりリクエストが許可されない | アカウントの残高または利用上限の設定を解決します。 |
| `403` | 認証情報のスコープまたはリソースへのアクセス権が不足している | 権限のあるキーまたはリソースを使用します。 |
| `404` | モデル、タスク、またはプラットフォームリソースが見つからない | 識別子と組織を確認します。 |
| `409` | リソースの状態または同時操作の競合 | 現在の状態を読み取ってから、リトライするかどうかを判断します。 |
| `429` | SandBase または上流プロバイダーがリクエストを制限した | `Retry-After` があればそれに従い、なければジッター付きでバックオフします。 |
| `500` / `502` / `503` / `504` | 内部、上流、または一時的な可用性の障害 | 操作を繰り返しても安全な場合にのみリトライします。 |

この表は対応のガイドであり、すべてのエンドポイントがすべてのステータスを返すことを保証するものではありません。

## 上限付きのリトライポリシーを使う {#use-a-bounded-retry-policy}

繰り返しても安全なリクエストには、ジッター付きのエクスポネンシャルバックオフを使い、遅延に上限を設け、リクエスト全体の予算を適用してください。
外側のアプリケーション層がすでにリトライしている場合は SDK のリトライを無効にするか、予算を設定する際に両方の層を考慮してください。

```python
import os
import random
import time

from openai import APIStatusError, OpenAI

client = OpenAI(
    base_url="https://api.sandbase.ai/v1",
    api_key=os.environ["SANDBASE_API_KEY"],
    max_retries=0,
)

def chat_with_backoff(messages, attempts=4):
    for attempt in range(attempts):
        try:
            return client.chat.completions.create(
                model="deepseek/deepseek-v4-flash",
                messages=messages,
            )
        except APIStatusError as error:
            retryable = error.status_code in {429, 500, 502, 503, 504}
            if not retryable or attempt == attempts - 1:
                raise
            delay = min(2 ** attempt, 30) + random.random()
            time.sleep(delay)
```

レスポンスに `Retry-After` が含まれる場合は、フォールバックの遅延を使わず、その値を解析して従ってください。ポリシーは
設定可能にしておいてください。適切な試行回数と期限は、呼び出し元のレイテンシとコストの予算によって異なります。

## 副作用の重複を防ぐ {#protect-against-duplicate-side-effects}

推論リクエストを繰り返すと新しい生成が作成され、追加のコストが発生する場合があります。これが許容されるのは、
アプリケーションが有効な回答であれば何でもよく、再生成を許容できる場合に限られます。

作成、更新、削除、公開、スケジュール、処理の呼び出しを行う操作では、より慎重に対応してください。

- エンドポイントが冪等性をサポートしている場合は、文書化された方法を使用します。
- そうでない場合は、結果が不明なリクエストを繰り返す前に現在の状態を読み取ります。
- 周囲のモデルストリームが切断されたという理由だけで、ツール呼び出しを再実行しないでください。
- リトライを照合する必要がある場合は、クライアントの操作 ID を自社システムで保持します。

## タイムアウトとストリームを区別して扱う {#handle-timeouts-and-streams-separately}

タイムアウトは、サーバーがリクエストの処理を停止したことを意味するわけではありません。非同期の操作や状態を変更する操作をリトライする前に、
可能であれば文書化されたリソースまたはタスクのステータスを照会してください。

ストリーミングレスポンスでは、ストリーム開始前の HTTP エラーと、部分的な出力後の切断を区別してください。
ストリームが完了したことを示すのは、プロトコルの通常の終了シグナルだけです。[ストリーミングレスポンス](/guides/streaming) を参照してください。

## 有用で安全な診断情報を記録する {#log-useful-safe-diagnostics}

次の情報を記録してください。

- エンドポイントとモデルの識別子
- HTTP ステータスと、存在する場合は互換エラーの type
- 返された場合はプロバイダーまたはリクエストの識別子
- 試行回数、経過時間、レスポンスのバイトが届いたかどうか

API キー、認証情報の値、機密性の高いプロンプト全体、未編集のプロバイダーレスポンスはログに記録しないでください。ユーザーには簡潔で
対処可能なメッセージを表示し、運用担当者向けにはサニタイズした診断情報を保持してください。
