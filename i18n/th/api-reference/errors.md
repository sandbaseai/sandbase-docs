# ข้อผิดพลาดของ API {#api-errors}

SandBase ใช้รหัสสถานะ HTTP มาตรฐาน แต่ไม่มี body ข้อผิดพลาดรูปแบบเดียวสำหรับทุกกรณี ให้แยกการจัดการตามสถานะ HTTP ก่อน จากนั้นจึงแยกวิเคราะห์ schema ของ response ที่ระบุไว้สำหรับ endpoint ที่คุณเรียก อย่ากำหนดให้ข้อผิดพลาดทุกรายการต้องมี `code`, `param`, `message` หรือ `request_id`

## รูปแบบของ response {#response-shapes}

middleware หลักและ endpoint `/v1/*` หลายรายการจะส่งคืนข้อผิดพลาดแบบแบน:

```json
{"error":"organization rate limit exceeded"}
```

รีซอร์สของแพลตฟอร์ม Agents (`/v1/agents*`, `/v1/mcp-connections*`, `/v1/secrets*`, `/v1/skills*`) จะส่งคืนออบเจ็กต์แบบ OpenAI ที่มี `code` คงที่ ดู[ข้อผิดพลาดของแพลตฟอร์ม Agents](#agents-platform-errors):

```json
{"error":{"type":"invalid_request_error","code":"invalid_request","param":null,"message":"invalid request"}}
```

Events API สำหรับ webhook (`/events/webhooks*`) จะส่งคืน `{"code":<http status>,"message":"..."}` ดู [Webhooks](/api-reference/webhooks#authentication-and-errors)

endpoint ที่เข้ากันได้กับ OpenAI จะคง envelope ที่เข้ากันได้กับ OpenAI ไว้ ส่วน `POST /v1/messages` จะคง envelope ที่เข้ากันได้กับ Anthropic ไว้:

```json
{
  "type": "error",
  "error": {
    "type": "invalid_request_error",
    "message": "max_tokens is required"
  }
}
```

ใช้[ข้อกำหนด OpenAPI](/openapi.yaml) เพื่อดูรหัสสถานะและ schema ที่ถูกต้องของการดำเนินการสาธารณะ

## การจัดการสถานะ HTTP {#http-status-handling}

| สถานะ | ความหมายโดยทั่วไป | สิ่งที่ไคลเอนต์ควรทำ |
|---|---|---|
| `400` | อินพุตไม่ถูกต้องหรือพารามิเตอร์ไม่รองรับ | แก้ไขคำขอตาม schema ของ endpoint และโมเดลที่เลือก |
| `401` | ข้อมูลรับรองหายไป ไม่ถูกต้อง ถูกเพิกถอน หรือหมดอายุ | เปลี่ยนหรือหมุนเวียนข้อมูลรับรอง อย่าลองใหม่โดยไม่เปลี่ยนแปลง |
| `402` | ไม่สามารถชำระค่าคำขอได้ หรือถึงขีดจำกัดการใช้จ่ายแล้ว | แก้ไขปัญหายอดคงเหลือหรือขีดจำกัดของคีย์ก่อนลองใหม่ |
| `403` | ข้อมูลรับรองไม่มีสิทธิ์ หรือ endpoint ด้านความเข้ากันได้แมปความล้มเหลวด้านการใช้จ่ายเป็น 403 | ตรวจสอบ envelope เฉพาะของ endpoint และใช้คีย์ที่ได้รับอนุญาต |
| `404` | ผู้เรียกใช้งานโมเดลหรือรีซอร์สไม่ได้ | ตรวจสอบ ID โมเดลหรือ ID รีซอร์สปัจจุบัน |
| `409` | สถานะของรีซอร์สขัดแย้งกัน | อ่านสถานะล่าสุดก่อนตัดสินใจว่าลองใหม่ได้อย่างปลอดภัยหรือไม่ |
| `422` | อินพุตของรีซอร์สไม่ถูกต้องตามความหมาย | แก้ไขค่าของฟิลด์ตามที่ระบุในเอกสาร |
| `429` | ขีดจำกัดคำขอขององค์กรหรือขีดจำกัดการทำงานพร้อมกันของวิดีโอ | ลองใหม่ด้วย backoff แบบมีขอบเขตและ jitter เมื่อการดำเนินการนั้นทำซ้ำได้อย่างปลอดภัย |
| `500`, `502`, `503`, `504` | ความล้มเหลวของ SandBase หรือต้นทาง | ลองใหม่เฉพาะเมื่อการดำเนินการนั้นทำซ้ำได้อย่างปลอดภัย |

ไม่ใช่ทุก endpoint ที่ระบุทุกสถานะในตารางนี้ แผนผัง response ของ OpenAPI สำหรับการดำเนินการนั้นถือเป็นข้อมูลอ้างอิงหลัก

## ข้อผิดพลาดในการยืนยันตัวตน {#authentication-errors}

ข้อความยืนยันตัวตนที่ระบุไว้ในเอกสารได้แก่:

- `missing API key in Authorization header`
- `invalid API key`
- `API key has been revoked`
- `API key has expired`

คีย์ที่จำกัดขอบเขตซึ่งถูกใช้นอกขอบเขตจะได้ `403` พร้อม body แบบซ้อนแทน: `{"error":{"code":"insufficient_scope","message":"API key is not authorized for this endpoint","request_id":"..."}}` รีซอร์สของแพลตฟอร์ม Agents จะส่งคืน `code` เดียวกันใน envelope ของตนเอง

ใช้ `Authorization: Bearer $SANDBASE_API_KEY` สำหรับ endpoint มาตรฐาน `POST /v1/messages` รับ `x-api-key` ได้ด้วย ส่วน endpoint ที่เข้ากันได้กับโปรโตคอลของ Google จะระบุเฮดเดอร์คีย์ที่รองรับไว้ในเอกสารของตนเอง

คีย์ที่ถูกเพิกถอนแล้วไม่สามารถเปิดใช้งานใหม่ได้ ให้สร้างคีย์ทดแทน อัปเดตแอปพลิเคชันที่ใช้คีย์ ตรวจสอบว่าใช้งานได้ แล้วจึงลบการอ้างอิงถึงคีย์เดิมที่เหลืออยู่

## ขีดจำกัดอัตรา {#rate-limits}

`organization rate limit exceeded` (`429`) หมายความว่าองค์กรของคุณถึงขีดจำกัดจำนวนคำขอต่อนาทีที่กำหนดไว้แล้ว ซึ่ง API key ทั้งหมดขององค์กรใช้ร่วมกัน endpoint ที่เข้ากันได้กับโปรโตคอลจะส่งคืนข้อผิดพลาดนี้ใน envelope ของตนเอง SandBase ไม่ได้เผยแพร่ตัวเลขขีดจำกัดค่าเดียวสำหรับทุกกรณี เนื่องจากขีดจำกัดกำหนดแยกตามองค์กร

หาก response มี `Retry-After` ให้ปฏิบัติตามค่านั้น มิฉะนั้นให้ใช้ exponential backoff แบบมีขอบเขตพร้อม jitter ดูรูปแบบการกระจายคำขอได้ที่[ขีดจำกัดอัตรา](/guides/rate-limiting)

การส่งงานมีการตรวจสอบเพิ่มเติมสองรายการ `organization concurrency limit exceeded` (`429`) หมายความว่าองค์กรของคุณมีงานที่กำลังดำเนินการอยู่เท่ากับจำนวนที่ระดับบัญชีอนุญาตแล้ว และจะหายไปเมื่องานที่กำลังรันเสร็จสิ้น ข้อจำกัดนี้ใช้กับโมเดลทุกประเภทบน `POST /v1/run` และ `/v1/api/*` และกับการส่งงานวิดีโอบน endpoint อื่น `insufficient credit for estimated video cost` (`402`) หมายความว่าค่าใช้จ่ายโดยประมาณสูงกว่ายอดคงเหลือรวมวงเงินเครดิตของคุณ ให้เติมเงินก่อนลองใหม่ ดู[ขีดจำกัดการทำงานพร้อมกัน](/guides/concurrency-limits)

## ความปลอดภัยในการลองใหม่ {#retry-safety}

ใช้ลำดับการตัดสินใจดังนี้:

1. พิจารณาว่าการดำเนินการได้สร้างผลกระทบที่มองเห็นได้จากภายนอกไปแล้วหรือไม่
2. อย่าลองคำขอ `400`, `401`, `402`, `403`, `404` หรือ `422` ใหม่โดยไม่เปลี่ยนแปลง
3. สำหรับ `409` ให้อ่านสถานะปัจจุบันของรีซอร์สก่อนลองใหม่
4. ลอง response `429` และ `5xx` ชั่วคราวใหม่เพียงไม่กี่ครั้งและมีขอบเขตจำกัด
5. ก่อนทำคำขอสร้าง ทริกเกอร์ อัปโหลด หรือการดำเนินการภายนอกซ้ำ ให้ยืนยันว่าการดำเนินการนั้นเป็น idempotent หรือแอปพลิเคชันของคุณจัดการรายการซ้ำได้

ระยะหน่วงเวลาที่เหมาะสมคือ:

```text
delay = min(base_delay * 2^attempt, max_delay) + random_jitter
```

## ข้อผิดพลาดของแพลตฟอร์ม Agents {#agents-platform-errors}

Agents, Sessions, Skills, การเชื่อมต่อ MCP และ Secrets ส่งคืน envelope รูปแบบเดียวกัน สำหรับโค้ดส่วนใหญ่ `message` เป็นประโยคคงที่ที่ปลอดภัย ส่วน `invalid_request` อาจมีคำอธิบายสั้น ๆ เช่น รูปแบบอินพุตหรือตัวเลือกใดที่ไม่รองรับ ให้แยกการจัดการตาม `code` ไม่ใช่ตาม `message`

```json
{"error":{"type":"invalid_request_error","code":"conflict","param":null,"message":"conflicting request"}}
```

`type` เป็น `authentication_error` สำหรับ 401, `server_error` สำหรับ 5xx และ `invalid_request_error` สำหรับกรณีอื่น

| HTTP | `code` | ความหมาย | สิ่งที่ควรทำ |
|---|---|---|---|
| 400 | `invalid_request` | ฟิลด์มีรูปแบบไม่ถูกต้องหรือไม่รู้จัก การตรวจสอบล้มเหลว หรือตัวเลือกไม่รองรับ | แก้ไขคำขอ อย่าลองใหม่โดยไม่เปลี่ยนแปลง |
| 400 | `skill_not_found` | Skill หรือเวอร์ชันที่อ้างอิงไม่พร้อมใช้งาน | แก้ไข `skills` ของ Agent |
| 401 | `unauthorized` | เฮดเดอร์ API key หายไป ไม่ถูกต้อง หรือขัดแย้งกัน | ตรวจสอบ `Authorization` / `X-API-Key` |
| 402 | `spending_limit_exceeded` | ขีดจำกัดการใช้จ่ายของคีย์หรือยอดคงเหลือขององค์กรหมดแล้ว | เพิ่มเครดิตหรือเพิ่มขีดจำกัด |
| 403 | `insufficient_scope` | คีย์ถูกจำกัดขอบเขตและใช้รีซอร์สของ Agents ไม่ได้ | ใช้คีย์มาตรฐานที่สร้างจาก Console |
| 403 | `org_disabled` | องค์กรไม่ได้รับอนุญาตให้รัน Agent | ติดต่อฝ่ายสนับสนุน |
| 404 | `not_found` | ไม่มีรีซอร์สนี้ในองค์กรของคุณ | ตรวจสอบ ID |
| 409 | `conflict` | `row_version` ล้าสมัย สถานะไม่อนุญาตให้เปลี่ยนแปลง หรือใช้ `Idempotency-Key` ซ้ำกับ body ที่ต่างกัน | อ่านรีซอร์สใหม่ แล้วจึงตัดสินใจ |
| 409 | `session_input_pending` | อินพุตก่อนหน้ายังอยู่ระหว่างการส่ง | รอ อย่าส่งซ้ำด้วยคีย์ใหม่ |
| 409 | `session_input_expired` | การรับอินพุตหมดเวลา | ตรวจสอบประวัติก่อนส่งอีกครั้ง |
| 409 | `session_environment_unavailable` | สภาพแวดล้อมการทำงานไม่พร้อมใช้งาน | รอหรือสร้าง Session ใหม่ |
| 413 | `request_too_large` | Request body หรือการกำหนดค่า Session ที่ตรึงจาก body นั้นเกินขีดจำกัดขนาด | ส่ง body ที่เล็กลง อย่าลองใหม่โดยไม่เปลี่ยนแปลง |
| 429 | `quota_exceeded` | เกินโควตาของ Agents | ลองใหม่ภายหลัง |
| 502 | `executor_rejected`, `executor_contract_error` | ชั้นการทำงานปฏิเสธคำขอหรือตอบกลับอย่างไม่คาดคิด | ตรวจสอบการกำหนดค่า Agent แล้วลองใหม่ |
| 503 | `executor_unavailable`, `storage_unavailable`, `skill_unavailable`, `tenant_unavailable`, `tenant_provisioning_failed`, `authorization_unavailable`, `admission_unavailable`, `internal_error` | ระบบที่ต้องพึ่งพาไม่พร้อมใช้งานชั่วคราว | ลองใหม่ด้วย backoff และ `Idempotency-Key` เดิม |

อาจพบ `skill_runtime_incompatible` ได้เช่นกัน โดยจะส่งคืนเป็น 503 พร้อมข้อความ `internal error`

## ความล้มเหลวระหว่างสตรีม {#streaming-failures}

หลังจากสตรีมเริ่มแล้ว ข้อผิดพลาดอาจมาในรูปแบบสตรีมของโปรโตคอลนั้นแทนที่จะเป็น HTTP response ใหม่ ให้ถือว่าสตรีมไม่สมบูรณ์ เก็บเอาต์พุตบางส่วนที่แอปพลิเคชันต้องใช้ไว้ และลองใหม่เฉพาะเมื่อการสร้างคำขอใหม่ทำได้อย่างปลอดภัย อย่าคาดว่าผู้ให้บริการทุกรายจะส่งเหตุการณ์สุดท้ายหรือ finish reason แบบเดียวกัน

## การดีบักในการใช้งานจริง {#operational-debugging}

บันทึก endpoint, สถานะ HTTP, ID โมเดลหรือรีซอร์สที่เลือก, timestamp และตัวระบุคำขอที่ปลอดภัยซึ่งเซิร์ฟเวอร์ส่งคืน ห้ามบันทึกเฮดเดอร์ authorization, API key, ค่าข้อมูลรับรอง หรือเนื้อหา prompt ที่ละเอียดอ่อนลงในล็อก

ใช้ [Developer → Activities](https://www.sandbase.ai/console/activities) เพื่อตรวจสอบประวัติคำขอขององค์กร เมื่อรายงานความล้มเหลวที่เกิดขึ้นต่อเนื่อง ให้แนบ metadata ของคำขอที่ลบข้อมูลละเอียดอ่อนแล้ว และคำขอที่เล็กที่สุดที่ทำให้เกิดปัญหาซ้ำได้
