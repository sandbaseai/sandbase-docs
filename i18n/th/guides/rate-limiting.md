# ขีดจำกัดอัตรา {#rate-limits}

SandBase สามารถกำหนดขีดจำกัดคำขอต่อนาทีให้องค์กรของคุณได้ ขีดจำกัดนี้ใช้ร่วมกันโดย API key ทุกตัวในองค์กร
และนับตามหน้าต่างเวลาแบบเลื่อนหนึ่งนาที ผู้ให้บริการโมเดลต้นทางก็อาจส่งคืนการตอบกลับ
`429 Too Many Requests` ของตนเองได้เช่นกัน อย่ากำหนดโควตาตายตัวในโค้ด เว้นแต่ SandBase ได้กำหนดโควตาให้เวิร์กโหลดของคุณ

## ขีดจำกัดขององค์กรคุณ {#your-organization-s-limit}
SandBase ไม่ได้เผยแพร่ตัวเลขคำขอต่อนาทีแบบตายตัว เพราะขีดจำกัดถูกกำหนดแยกตามองค์กร
API key ทุกตัวในองค์กรนับรวมในขีดจำกัดเดียวกัน การสร้างคีย์เพิ่มจึงไม่ได้เพิ่มขีดจำกัด ปัจจุบันขีดจำกัดนี้
ไม่ได้แสดงใน API สาธารณะหรือ Console

หากเวิร์กโหลดของคุณต้องการขีดจำกัดที่รับประกันหรือสูงขึ้น ให้ติดต่อฝ่ายสนับสนุนของ SandBase พร้อมระบุองค์กร แอปพลิเคชัน
อัตราปกติที่คาดไว้ และอัตราช่วงพีกที่คาดไว้ อย่าออกแบบไคลเอนต์สำหรับโปรดักชันโดยอิงค่าเริ่มต้นที่เป็นตัวเลขซึ่งไม่ได้ระบุไว้ในเอกสาร

## จัดการการตอบกลับ 429 {#handle-a-429-response}

การตอบกลับขีดจำกัดอัตราของ `/v1/*` ที่สร้างโดยแพลตฟอร์มใช้ error body แบบแบน:

```http
HTTP/1.1 429 Too Many Requests
Content-Type: application/json

{"error":"organization rate limit exceeded"}
```

ขีดจำกัดขององค์กรใช้กับ `POST /v1/run`, `POST /v1/chat/completions`, `POST /v1/responses`, `POST /v1/messages`, `POST /v1/upload` และ endpoint ของ Gemini ได้แก่ `generateContent`, `streamGenerateContent` และ `POST /v1beta/interactions` ส่วน endpoint สำหรับ poll เช่น
`GET /v1/run/{id}` จะไม่ถูกนับ endpoint ที่เข้ากันได้กับโปรโตคอลอื่นจะส่งคืน `429` เดียวกันในรูปแบบข้อผิดพลาดของตนเอง
เช่น รูปแบบข้อผิดพลาดของ Anthropic หรือ Google การตอบกลับที่มาจากผู้ให้บริการอาจใช้รูปแบบข้อผิดพลาดของ
endpoint ที่เข้ากันได้ และอาจมีเฮดเดอร์ขีดจำกัดอัตราของผู้ให้บริการ

ไม่รับประกันว่าจะมีเฮดเดอร์ `Retry-After` และเฮดเดอร์โควตาคงเหลือ หากมี `Retry-After` ให้ปฏิบัติตาม มิฉะนั้นให้ใช้
exponential backoff พร้อม jitter และกำหนดจำนวนครั้งสูงสุด

```python
import os
import random
import time

from openai import OpenAI, RateLimitError

client = OpenAI(
    base_url="https://api.sandbase.ai/v1",
    api_key=os.environ["SANDBASE_API_KEY"],
    max_retries=0,
)

def create_with_backoff(**request):
    for attempt in range(5):
        try:
            return client.chat.completions.create(**request)
        except RateLimitError:
            if attempt == 4:
                raise
            delay = min(2 ** attempt, 30) + random.random()
            time.sleep(delay)
```

OpenAI SDK ยังรองรับการลองใหม่ในตัวผ่าน `max_retries` ด้วย ให้เลือกใช้การลองใหม่ของ SDK หรือลูปการลองใหม่ของแอปพลิเคชัน
อย่างใดอย่างหนึ่งอย่างตั้งใจ เพื่อไม่ให้การลองใหม่ทวีคูณข้ามชั้น

## ลองใหม่เฉพาะการดำเนินการที่ปลอดภัย {#retry-only-safe-operations}

คำขอ inference ที่ส่งซ้ำอาจสร้างผลลัพธ์ครั้งที่สองและมีค่าใช้จ่ายเพิ่ม ให้ลองใหม่เฉพาะเมื่อ
แอปพลิเคชันของคุณยอมรับการสร้างซ้ำได้ อย่าลองคำขอที่เปลี่ยนสถานะซ้ำโดยอัตโนมัติ เว้นแต่การดำเนินการนั้นระบุ
idempotency ไว้ หรือแอปพลิเคชันของคุณพิสูจน์ได้ว่าความพยายามครั้งแรกไม่สำเร็จ

สำหรับคำขอแบบสตรีม `429` มักมาถึงก่อนสตรีมเริ่ม เมื่อได้รับข้อมูลแล้ว ให้ถือว่าการเชื่อมต่อหลุด
เป็นการสร้างที่ถูกขัดจังหวะ ไม่ใช่ข้อผิดพลาดขีดจำกัดอัตรา เก็บหรือทิ้งเอาต์พุตบางส่วนตาม
ข้อกำหนดของผลิตภัณฑ์ การเริ่มใหม่จะเป็นการสร้างครั้งใหม่

## ควบคุมปริมาณงาน {#control-throughput}

- จำกัดการทำงานพร้อมกันแทนการปล่อยแบตช์ที่ไม่จำกัดออกไปพร้อมกัน
- จัดคิวงานที่เข้ามาเป็นช่วงๆ และทำให้อัตราการส่งสม่ำเสมอ
- หลีกเลี่ยงคำขอซ้ำ และแคชผลลัพธ์ที่นำกลับมาใช้ได้เมื่อข้อกำหนดด้านความเป็นส่วนตัวและความสดใหม่ของข้อมูลอนุญาต
- ใช้คีย์แยกกันเพื่อแบ่งความเป็นเจ้าของ การควบคุมการใช้จ่าย และการเพิกถอน ไม่ใช่เพื่อหลบเลี่ยงขีดจำกัดของแพลตฟอร์ม
- บันทึก endpoint, โมเดล, สถานะ HTTP และ error body ที่กรองข้อมูลละเอียดอ่อนแล้วเพื่อใช้แก้ปัญหา
- ติดต่อฝ่ายสนับสนุนของ SandBase เมื่อเวิร์กโหลดต้องการขีดจำกัดความจุที่กำหนดให้หรือสูงขึ้น

```python
import asyncio

semaphore = asyncio.Semaphore(8)

async def run_one(client, prompt):
    async with semaphore:
        return await client.chat.completions.create(
            model="deepseek/deepseek-v4-flash",
            messages=[{"role": "user", "content": prompt}],
        )
```

การทำงานพร้อมกันไม่เหมือนกับคำขอต่อนาที ให้ปรับทั้งสองค่าตาม latency ที่สังเกตได้และความจุที่กำหนดให้
แอปพลิเคชันของคุณ

::: info การเรียก API ฟรีรายวัน
การเรียก API ข้อมูลฟรี 100 ครั้งต่อวันตามเวลา UTC ขององค์กรเป็นโควตาด้านการเรียกเก็บเงิน ไม่ใช่ขีดจำกัดอัตรา การเรียกที่เกินจะ
ถูกเรียกเก็บเงินต่อครั้งแทนการถูกปฏิเสธ ดู [การเรียก API ฟรีรายวัน](/guides/billing#daily-free-api-calls)
:::
