# ข้อผิดพลาดและการลองใหม่ {#errors-and-retries}

จัดการข้อผิดพลาดตามสถานะ HTTP กลุ่มของเอนด์พอยต์ และความหมายของการดำเนินการ SandBase เปิดให้ใช้หลายโปรโตคอลที่เข้ากันได้
จึงไม่มีรูปแบบ JSON ของข้อผิดพลาดแบบเดียวที่ทุกเอนด์พอยต์ใช้ร่วมกัน

## อ่านรูปแบบข้อผิดพลาดของเอนด์พอยต์ {#read-the-endpoint-s-error-shape}

- การดำเนินการที่เข้ากันได้กับ OpenAI มักส่งคืนออบเจ็กต์ `error` พร้อม message และ type
- Anthropic Messages ส่งคืน envelope ข้อผิดพลาดที่เข้ากันได้กับ Anthropic
- การดำเนินการหลักของแพลตฟอร์มอาจส่งคืนเนื้อหาแบบแบน `{ "error": "..." }` หรือข้อผิดพลาดเฉพาะทรัพยากรที่ระบุไว้ในเอกสาร
- การดำเนินการของ Google และแบบเนทีฟของผู้ให้บริการจะคงรูปแบบโปรโตคอลที่เข้ากันได้ไว้ตามที่ระบุในเอกสาร

ใช้สถานะ HTTP ของการตอบกลับและเนื้อหาที่ระบุในเอกสาร อย่าบังคับให้มีฟิลด์ที่ไม่บังคับ เช่น `code`, `param` หรือ
`request_id` เว้นแต่เอนด์พอยต์ที่เลือกจะรับประกันว่ามี ดูตัวอย่างได้ที่[เอกสารอ้างอิงข้อผิดพลาดของ API](/api-reference/errors) และดู
การตอบกลับเฉพาะของแต่ละการดำเนินการได้ที่[ข้อกำหนด OpenAPI](/openapi.yaml)

## ตัดสินใจตามสถานะ {#decide-what-to-do-by-status}

| สถานะ | สาเหตุที่พบบ่อย | สิ่งที่แนะนำให้ทำ |
|---|---|---|
| `400` / `422` | เนื้อหาหรือพารามิเตอร์ไม่ถูกต้อง หรือโมเดลไม่รองรับความสามารถนั้น | แก้ไขคำขอก่อนลองใหม่ |
| `401` | ไม่มีข้อมูลรับรอง หรือข้อมูลรับรองไม่ถูกต้อง หมดอายุ หรือถูกเพิกถอน | เปลี่ยนข้อมูลรับรอง |
| `402` | สถานะการเรียกเก็บเงินไม่อนุญาตให้ทำคำขอ | แก้ไขยอดเงินในบัญชีหรือการควบคุมการใช้จ่าย |
| `403` | ขอบเขตของข้อมูลรับรองหรือสิทธิ์เข้าถึงทรัพยากรไม่เพียงพอ | ใช้คีย์หรือทรัพยากรที่ได้รับอนุญาต |
| `404` | ไม่พบโมเดล งาน หรือทรัพยากรของแพลตฟอร์ม | ตรวจสอบตัวระบุและองค์กร |
| `409` | สถานะของทรัพยากรหรือการดำเนินการพร้อมกันขัดแย้งกัน | อ่านสถานะปัจจุบัน แล้วจึงตัดสินใจว่าจะลองใหม่หรือไม่ |
| `429` | SandBase หรือผู้ให้บริการต้นทางจำกัดคำขอ | ทำตาม `Retry-After` หากมี มิฉะนั้นให้ถอยเวลาพร้อม jitter |
| `500` / `502` / `503` / `504` | ความล้มเหลวภายใน จากต้นทาง หรือความไม่พร้อมใช้งานชั่วคราว | ลองใหม่เฉพาะเมื่อการทำซ้ำปลอดภัยเท่านั้น |

ตารางนี้เป็นแนวทางในการจัดการ ไม่ได้รับประกันว่าทุกเอนด์พอยต์จะส่งคืนทุกสถานะ

## ใช้นโยบายการลองใหม่ที่มีขอบเขต {#use-a-bounded-retry-policy}

สำหรับคำขอที่ทำซ้ำได้อย่างปลอดภัย ให้ใช้ exponential backoff พร้อม jitter จำกัดระยะหน่วงสูงสุด และบังคับใช้งบประมาณคำขอรวม
ปิดการลองใหม่ของ SDK หากชั้นแอปพลิเคชันภายนอกลองใหม่อยู่แล้ว หรือคำนึงถึงทั้งสองชั้นเมื่อกำหนดงบประมาณ

```python
import os
import random
import time

from openai import APIStatusError, OpenAI

client = OpenAI(
    base_url="https://api.sandbase.ai/v1",
    api_key=os.environ["SANDBASE_API_KEY"],
    max_retries=0,
)

def chat_with_backoff(messages, attempts=4):
    for attempt in range(attempts):
        try:
            return client.chat.completions.create(
                model="deepseek/deepseek-v4-flash",
                messages=messages,
            )
        except APIStatusError as error:
            retryable = error.status_code in {429, 500, 502, 503, 504}
            if not retryable or attempt == attempts - 1:
                raise
            delay = min(2 ** attempt, 30) + random.random()
            time.sleep(delay)
```

เมื่อการตอบกลับมี `Retry-After` ให้แยกวิเคราะห์และทำตามค่านั้นแทนการใช้ระยะหน่วงสำรอง ทำให้นโยบาย
ปรับแต่งได้ เพราะจำนวนครั้งและกำหนดเวลาที่เหมาะสมขึ้นอยู่กับงบประมาณด้านเวลาแฝงและค่าใช้จ่ายของผู้เรียก

## ป้องกันผลข้างเคียงที่ซ้ำซ้อน {#protect-against-duplicate-side-effects}

การส่งคำขออนุมานซ้ำจะสร้างผลลัพธ์ใหม่และอาจมีค่าใช้จ่ายเพิ่ม ซึ่งยอมรับได้เฉพาะเมื่อ
แอปพลิเคชันต้องการคำตอบที่ถูกต้องใดก็ได้และรับการสร้างใหม่ได้

ให้ระมัดระวังมากขึ้นกับการดำเนินการที่สร้าง อัปเดต ลบ เผยแพร่ ตั้งเวลา หรือเรียกใช้งาน:

- ใช้การรองรับ idempotency ที่ระบุในเอกสารเมื่อเอนด์พอยต์มีให้
- มิฉะนั้น ให้อ่านสถานะปัจจุบันก่อนส่งคำขอที่ผลลัพธ์ไม่ชัดเจนซ้ำ
- อย่าเรียกเครื่องมือซ้ำเพียงเพราะสตรีมของโมเดลที่ครอบอยู่ขาดการเชื่อมต่อ
- เก็บ ID การดำเนินการฝั่งไคลเอนต์ไว้ในระบบของคุณเองเมื่อต้องกระทบยอดการลองใหม่

## จัดการการหมดเวลาและสตรีมแยกกัน {#handle-timeouts-and-streams-separately}

การหมดเวลาไม่ได้พิสูจน์ว่าเซิร์ฟเวอร์หยุดประมวลผลคำขอแล้ว ก่อนลองการดำเนินการแบบอะซิงโครนัสหรือที่เปลี่ยนสถานะใหม่
ให้คิวรีสถานะของทรัพยากรหรืองานที่ระบุในเอกสารเมื่อทำได้

สำหรับการตอบกลับแบบสตรีม ให้แยกข้อผิดพลาด HTTP ก่อนเริ่มสตรีมออกจากการขาดการเชื่อมต่อหลังได้เอาต์พุตบางส่วน
มีเพียงสัญญาณสิ้นสุดตามปกติของโปรโตคอลเท่านั้นที่พิสูจน์ว่าสตรีมสมบูรณ์ ดู[การตอบกลับแบบสตรีม](/guides/streaming)

## บันทึกข้อมูลวินิจฉัยที่มีประโยชน์และปลอดภัย {#log-useful-safe-diagnostics}

บันทึก:

- เอนด์พอยต์และตัวระบุโมเดล
- สถานะ HTTP และประเภทข้อผิดพลาดที่เข้ากันได้ (ถ้ามี)
- ตัวระบุของผู้ให้บริการหรือคำขอ (เมื่อมีการส่งคืน)
- จำนวนครั้งที่ลอง เวลาที่ผ่านไป และมีไบต์ของการตอบกลับมาถึงหรือไม่

อย่าบันทึก API key ค่าข้อมูลรับรอง prompt ที่ละเอียดอ่อนทั้งหมด หรือการตอบกลับของผู้ให้บริการที่ยังไม่ได้ปกปิดข้อมูล แสดงข้อความที่กระชับ
และนำไปปฏิบัติได้แก่ผู้ใช้ ขณะเก็บข้อมูลวินิจฉัยที่ผ่านการกรองแล้วไว้ให้ผู้ดูแลระบบ
